# 要件定義

## 1. 目的

個人向けの家計簿アプリ。iOS / Android の両方で動作し、日々の支出・収入の記録と、
予算に対する進捗の把握を行う。

## 2. 前提条件

このアプリの設計を規定している3つの決定事項。

| 項目 | 決定 | 影響 |
|---|---|---|
| データの置き場所 | **端末内のみ**（サーバーを持たない） | 同期・共有機能なし。バックアップはユーザー操作 |
| 配布 | **App Store / Google Play で一般公開** | 審査対応・プライバシー表示・データ移行手段が必須 |
| 開発言語 | **TypeScript** | React Native (Expo) を採用 |
| 収益化 | **買い切り課金 + バナー広告** | 広告SDKが識別子を送るため「完全に端末内で完結」ではなくなった |

家計簿の中身（取引・予算・貯金）は端末内にしか無く、同期用のサーバーも持たない。
ただし **広告SDKは配信のために端末識別子を Google に送る**ため、
「一切外部と通信しない」とは言えなくなっている。
ストアの申告と説明では、この線引きを正確に書くこと（→ [06-monetization.md](./06-monetization.md)）。
一方で、**機種変更時のデータ移行手段がアプリ内に無いと詰む**という制約が生まれるため、
バックアップ／復元は第一版から必須機能として扱う（→ [FR-5](#fr-5-バックアップ復元)）。

## 3. 機能要件

### FR-1: 支出と収入を別で管理できる

- すべての取引は `支出` / `収入` のいずれかの種別を持つ
- カテゴリも種別ごとに分かれる（支出カテゴリと収入カテゴリは混ざらない）
- 集計は種別ごとに独立して行い、収支（収入 − 支出）を併せて表示する
- 金額は常に正の値で保持し、符号ではなく種別で収支を判別する

**実装上の判断**: テーブルを `expenses` / `incomes` に分けるのではなく、
`transactions` 1テーブル + `type` カラムで表現する。
分割すると、将来「口座間の振替」を追加したくなった時点で破綻し、
また「今月の全取引を日付順に並べる」という最も基本的な操作が UNION になる。

### FR-2: 毎月／毎年の予算を設定できる

- 予算の単位は **月次** と **年次** の2種類
- それぞれについて、**全体予算**（支出合計の上限）と **カテゴリ別予算** を設定できる
- 「既定値」と「特定期間の上書き」を区別する
  - 既定: 「毎月の食費は 30,000 円」→ 以降すべての月に適用
  - 上書き: 「ただし 12 月だけ 50,000 円」→ その月だけ差し替え
- 予算に対する消化率を色（緑 / 橙 / 赤）と数値の両方で表示する
- 当月については「月の経過割合」をバー上に印として出し、使うペースが速いかを示す

**実装上の判断**: 上書きを別テーブルにせず、同じ `budgets` テーブルの
`year` / `month` が 0 かどうかで既定と上書きを区別する（→ [DB設計](./03-data-model.md#budgets)）。
解決順は「特定期間 → 既定 → 未設定」。

### FR-3: 固定費等の設定ができる

- 繰り返し発生する支出・収入（家賃、通信費、サブスク、給与など）を登録できる
- 繰り返し規則は **毎月N日 / 毎年M月N日 / 毎週W曜** の3種類
  - 毎月31日など、その月に存在しない日は月末に丸める
- 開始日と終了日（任意）を持つ
- **登録方式を2つから選べる**
  - **継続して自動**: 規則を保存し、期日が来るたびに自動で記録する
  - **まとめて追加**: 規則は保存せず、指定した期間の該当日ぶんを**その場で一括記録**する
    （終了日が必須。一度に最大 500 件）
- 継続方式では、さらに反映方式を2つから選べる
  - **自動計上**: 期日が来たらアプリ起動時に自動で取引を作る
  - **手動確定**: 期日が来たらホーム画面に「確認待ち」として出し、承認したら計上する
    （金額が毎回変動する光熱費などを想定）
- 発生の N 日前にローカル通知を出せる（当日 / 前日 / 3日前 / 1週間前）
- 一時停止（無効化）ができ、無効中は計上も通知もされない

**実装上の判断**: `rrule` 等の汎用繰り返しライブラリは使わない。
表現力は高いが設定 UI が一気に複雑になる割に、家計簿の固定費で
「第2火曜日」「2ヶ月ごと」が必要になる場面はほとんどない。

「まとめて追加」で作られるのは **通常の取引** で、固定費（`recurrings`）の行は作らない。
過去にさかのぼって家賃を入れる、今年ぶんの年会費を先に入れておく、といった
「もう決まっている出費を一度で入れたい」用途を想定している。
そのぶん `recurring_id` が付かないため二重生成をユニーク索引で防げないので、
実行前に件数と期間を示す確認ダイアログを必ず挟む。

### FR-7: 貯金

- 「目的・目標金額・目標日」を持つ貯金の目標を作れる（目標日は任意）
- 記録画面と固定費に **貯金専用の枠** があり、目標を選んで積み立てる
- 目標ごとに 積立額 / 目標額 / 達成率 / 残額 を表示する
- 目標日がある場合は「毎月いくら積めば届くか」と、
  今のペースで間に合うかの見通しを出す
- 達成済み・中止した目標はアーカイブできる（積立の記録は残る）

**実装上の判断**: 貯金を **支出の一種にせず、独立した種別** にしている。

支出に混ぜると生活費の集計と予算の消化率が実態より膨らみ、
「使っていないのに予算オーバー」という表示になる。
収入に混ぜれば入ってきたお金として二重に数えてしまう。
別種別にすれば既存の集計（income / expense）はそのままで、貯金だけを足し引きできる。

**集計上は貯金も「出ていったお金」として扱う。**

| 指標 | 計算 |
|---|---|
| 全体の支出 | 支出 + 貯金 |
| 収支 | 収入 − 支出 − 貯金 |
| 全体予算の消化 | 支出 + 貯金 |

積立に回した額を収支に残したままだと、まだ使えるお金を多く見積もってしまい
月末に足りなくなる。置き場所が変わっただけであっても、家計簿として見たいのは
「あといくら使えるか」なので支出側で数える。

ただし **カテゴリ別予算には入らない**。貯金にカテゴリは無いため、
予算画面では「予算未設定の支出」として別行に並ぶ。
ホームとレポートの内訳（円グラフ）にも「貯金」の枠を出し、
内訳の合計が全体の支出と一致するようにしている。

貯金の分類名は積立先の目標を使う（`貯金・沖縄旅行`）。
カテゴリを持たないため、そのままでは一覧で「未分類」と出てしまうため。

### FR-8: 収益化

- **買い切り課金**（非消耗型・¥500）で次を解放する
  - 貯金機能（FR-7）
  - 広告の非表示
- 未購入でも貯金の枠は表示し、鍵アイコンから課金画面へ誘導する
- **「購入を復元」** を課金画面に置く（非消耗型では必須）
- 広告はバナーのみ。ホームと履歴の最下部に出す

**実装上の判断**: 詳細と審査対応は [06-monetization.md](./06-monetization.md) に分けてある。
所持状態の控えは「購入済み」を保つ方向にしか使わない
（通信できないだけで機能を取り上げないため）。

### FR-4: 記録・閲覧

- 取引の追加・編集・削除
- 月単位での一覧（日付ごとにグループ化し、日計を表示）
- 支出／収入／すべて でのフィルタ
- カテゴリ別の内訳（円グラフ）
- 年間レポート（月ごとの収支推移、年間予算の消化、カテゴリ内訳）

### FR-5: バックアップ／復元

**このアプリで最も重要な非機能に近い機能要件。**

- JSON 形式でのバックアップ書き出し（共有シート経由で iCloud Drive / Google Drive 等へ保存）
- バックアップからの復元（全置換。マージはしない）
- CSV 書き出し（Excel / Numbers で開ける、BOM 付き UTF-8）
- 全データ削除（「削除」と入力させる二重確認つき）

保険は二重にかける。

1. **明示的なエクスポート／インポート**（上記、アプリが実装する）
2. **OS 標準バックアップ**（自動で効く）
   - iOS: `Documents` 配下は iCloud バックアップの対象。`expo-sqlite` の DB もここに置かれる
   - Android: `android.allowBackup = true` により Auto Backup 対象

2 は無料で効くが、ユーザーが機能をオフにしている場合があるため 1 単独で完結できる必要がある。

### FR-6: カテゴリ管理

- 追加・改名・アイコン変更・色変更
- **記録の入力中にも追加できる**（カテゴリ選択の末尾の「追加」から）
- **アーカイブ**（新規入力の候補から外すが、過去の記録は保持）
- 削除は、そのカテゴリを使う取引が 0 件のときのみ許可

**実装上の判断**: 入力の途中でカテゴリを足せるようにする。
「設定画面まで戻って作ってから入力し直す」往復は、記録をやめる一番の理由になる。
入力の流れを切らずに足せることを優先し、作成 UI は名前・アイコン・色だけに絞ってある。

使用中のカテゴリは削除させない。
削除を許すと過去の集計が「未分類」に化けて履歴の意味が変わる。
アーカイブという逃げ道を用意することで、削除したい動機（一覧から消したい）は満たせる。

## 4. 非機能要件

| 項目 | 要件 |
|---|---|
| オフライン | 全機能がオフラインで動作すること（ネットワーク通信を一切行わない） |
| 起動速度 | 起動時の処理は マイグレーション + 固定費の計上 + 通知の再登録 のみ |
| データ整合性 | 金額は整数（円）。浮動小数を DB にもロジックにも持ち込まない |
| テーマ | **既定はライト**。ダークは設定から明示的に選ぶ（端末に追従も選べる） |
| アクセシビリティ | 予算の超過を色だけで伝えない（数値と文言を併記する） |

## 5. スコープ外（第一版では作らない）

意図的に外したもの。将来的に追加する場合の影響も併記する。

| 項目 | 理由 | 追加する場合 |
|---|---|---|
| 複数端末での同期 | サーバーが必要になり、要件の前提と矛盾する | Supabase 等のバックエンド + 競合解決が必要 |
| 家族・パートナーとの共有 | 同上（認証と権限管理が発生する） | 同上 |
| 銀行・クレカの自動連携 | 金融機関 API の契約と審査、セキュリティ責任が発生する | 事業としての体制が必要 |
| レシートの OCR 読み取り | 端末内 OCR は精度が不安定、クラウド OCR は外部送信になる | 外部送信を許容するか要判断 |
| 口座間の振替 | 「資産管理」の要件が入ると設計が一段複雑になる | `transactions` に `transfer` 種別と口座テーブルを追加 |
| 締め日の変更（給料日基準など） | 実装済みの下地（`settings.month_start_day`）はあるが UI 未実装 | 月範囲の計算を差し替えるだけで対応可能 |
| 多通貨 | 日本円のみを想定 | 金額を最小通貨単位 + 通貨コードで持つ設計にはなっている |

## 6. 用語

| 用語 | 意味 |
|---|---|
| 取引 (transaction) | 1件の支出または収入の記録 |
| 種別 (type) | `expense`（支出） / `income`（収入） |
| 固定費 (recurring) | 繰り返し発生する取引の「テンプレート」。それ自体は取引ではない |
| 発生 (occurrence) | 固定費の規則から算出される、1回分の予定日 |
| 計上 (post) | 固定費の発生から実際の取引レコードを作ること |
| 既定予算 | 期間を限定しない予算。以降すべての月／年に適用される |
| 上書き予算 | 特定の年月／年だけに適用される予算 |
